Retrieval-Augmented Generation (RAG) — Grounding LLMs in Real Data

May 21, 2026 · Document Chunking · Vector Embeddings · Similarity Search · Grounded Generation

The Lesson

Large language models are impressive, but they have a fundamental limitation: their knowledge is frozen at training time. If you ask an LLM about an event that happened yesterday, a company's internal policy, or a proprietary dataset it was never trained on, it will either hallucinate an answer or admit ignorance. Retrieval-Augmented Generation (RAG) solves this by giving the model access to external documents at inference time.

RAG works in three stages. Indexing splits a document corpus into smaller chunks and converts each chunk into a dense vector embedding using an embedding model. Retrieval takes the user's query, embeds it with the same model, and finds the most similar document chunks using cosine similarity. Generation feeds the retrieved chunks as context to the LLM along with the original question, so the model generates an answer grounded in real, traceable sources.

The beauty of RAG is that it separates knowledge from model weights. Instead of fine-tuning the model on new data (expensive, slow, and degrades general capabilities through catastrophic forgetting), you simply add documents to your vector store. The model stays the same; the knowledge base grows. This makes RAG the default architecture for enterprise AI applications — customer support bots, document Q&A systems, knowledge bases, and legal/medical assistants.

The critical design decisions in RAG are: chunk size (too small loses context, too large dilutes relevance), overlap (ensures boundaries between chunks don't split important information), embedding model choice (determines retrieval quality), and prompt template (instructs the LLM how to use retrieved context). Getting these right is what separates a working RAG system from a production-grade one.

Concrete Example

Step 1 — Document Chunking with Overlap

Split documents into manageable chunks with overlap to preserve context at boundaries. Here's a simplified chunking function:

import tiktoken

def chunk_text(text: str, max_tokens: int = 600, overlap: int = 150) -> list[str]:
    """Split text into chunks with token-level overlap."""
    encoder = tiktoken.get_encoding("cl100k_base")
    tokens = encoder.encode(text)
    step = max_tokens - overlap
    chunks = []
    for i in range(0, len(tokens), step):
        chunk_tokens = tokens[i:i + max_tokens]
        chunk_text = encoder.decode(chunk_tokens)
        chunks.append(chunk_text)
    return chunks

# Example usage
document = "The Transformer architecture was introduced in 2017 by Vaswani et al. " * 50
chunks = chunk_text(document, max_tokens=600, overlap=150)
print(f"Split into {len(chunks)} chunks")
# → Split into 5 chunks

Step 2 — Embedding and Vector Store

Convert chunks and queries into vectors, then find the most relevant chunks using cosine similarity:

import numpy as np

def cosine_similarity(v1: np.ndarray, v2: np.ndarray) -> float:
    """Compute cosine similarity between two vectors."""
    dot = np.dot(v1, v2)
    norm = np.linalg.norm(v1) * np.linalg.norm(v2)
    return dot / norm if norm > 0 else 0.0

class SimpleVectorStore:
    """Minimal vector store for RAG retrieval."""

    def __init__(self):
        self.documents = []
        self.vectors = []

    def add(self, text: str, embedding: list[float]):
        self.documents.append(text)
        self.vectors.append(np.array(embedding, dtype=np.float32))

    def query(self, query_embedding: list[float], k: int = 3) -> list[tuple[str, float]]:
        """Return top-k most similar documents with scores."""
        q = np.array(query_embedding, dtype=np.float32)
        scores = [cosine_similarity(q, v) for v in self.vectors]
        # Get indices of top-k scores, sorted descending
        top_k = np.argsort(scores)[-k:][::-1]
        return [(self.documents[i], scores[i]) for i in top_k]

# Example usage
store = SimpleVectorStore()
store.add("RAG reduces hallucinations by grounding answers in retrieved documents.",
          [0.9, 0.1, 0.0])  # hypothetical embedding
store.add("The attention mechanism computes weighted sums of values.",
          [0.1, 0.8, 0.3])
store.add("RAG systems use vector embeddings for semantic search.",
          [0.85, 0.15, 0.05])

# Query: "How does RAG help with hallucinations?"
query_vec = [0.88, 0.12, 0.02]
results = store.query(query_vec, k=2)
for doc, score in results:
    print(f"  [{score:.3f}] {doc[:60]}...")
# → [0.999] RAG reduces hallucinations by grounding answers in retrieved...
# → [0.997] RAG systems use vector embeddings for semantic search...

Step 3 — Generation with Retrieved Context

The final step: inject retrieved context into the prompt and let the LLM generate a grounded answer:

RAG_PROMPT = """Use the following context to answer the question.
If you don't know the answer, say you don't know.

Question: {question}

Context:
---
{context}
---

Answer:"""

def generate_answer(llm_client, question: str, context_chunks: list[str], model: str) -> str:
    """Generate a grounded answer using retrieved context."""
    context = "\n\n".join(context_chunks)
    prompt = RAG_PROMPT.format(question=question, context=context)
    response = llm_client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}],
        temperature=0.1,  # Low temperature for factual answers
        max_tokens=1024,
    )
    return response.choices[0].message.content

# Full pipeline
retrieved_docs = [doc for doc, _ in store.query(query_vec, k=2)]
answer = generate_answer(client, "How does RAG reduce hallucinations?", retrieved_docs, "gpt-4o-mini")
print(answer)
Key Takeaway: RAG is not a model — it's an architecture pattern. The same LLM can answer questions about any domain simply by changing the document corpus it retrieves from. The formula is simple: Answer = LLM(Query + RetrievedContext). The engineering challenge is making retrieval accurate enough that the context actually helps rather than distracts.

Why It Matters

In production, RAG is the most widely deployed LLM pattern. Here's why:

  • Hallucination reduction. By grounding answers in retrieved documents, RAG gives the model factual anchors. Studies show RAG can reduce hallucination rates by 30-50% compared to raw LLM generation on domain-specific questions.
  • Zero fine-tuning needed. Adding new knowledge means adding documents to the vector store — no retraining, no compute costs, no catastrophic forgetting. This is how companies keep their AI assistants current without retraining models monthly.
  • Traceability and auditability. Every RAG answer can cite its source documents. In regulated industries (legal, medical, finance), this is not optional — it's a compliance requirement.
  • Cost efficiency. A small open-source model with good RAG retrieval often outperforms a larger model without retrieval on domain-specific tasks. You pay for the right tool, not the biggest model.

The RAG pipeline is the backbone of tools like LangChain, LlamaIndex, and enterprise search products. Understanding chunking strategies, embedding quality, and retrieval ranking is the difference between a demo that works and a system your customers trust.

Lesson 11 Chapter 4

LLM Scaling Laws — The Math Behind Bigger Models

Source: Happy-LLM Chapter 4 — Large Language Models • May 15, 2026

The Lesson

Before 2020, building NLP models was mostly an art. You picked an architecture, tuned hyperparameters, and hoped for the best. Then OpenAI published their Scaling Laws paper, and everything changed. They showed that model performance follows predictable, mathematical relationships with three variables: the number of parameters (N), the amount of training data (D), and the total compute budget (C).

The core insight is deceptively simple. The total compute required to train a model is approximately:

C  ∼  6   N   D

Where C is total floating-point operations (FLOPs), N is the number of model parameters, and D is the number of training tokens. The factor of 6 comes from the fact that each forward-backward pass through a transformer requires roughly 6 FLOPs per parameter per token (2 for the forward pass, 2 for the backward pass, and 2 for optimizer updates in Adam).

But the formula alone doesn't tell you how to allocate your budget. OpenAI found that for a fixed compute budget, the optimal amount of data is roughly 1.7 times the number of parameters. LLaMA went further, showing that using 20 times as many tokens as parameters yields the best results — meaning GPT-3's 175B parameter model could have been trained on 3.5 trillion tokens instead of 300 billion for significantly better performance.

This means there is a correct answer to "how big should my model be?" and "how much data do I need?" — and the answer depends entirely on your compute budget. If you have 100 A100 GPUs for one week, the scaling laws tell you exactly how to split that budget between model size and data volume. This is why modern LLM development is less about architecture innovation and more about resource planning.

Concrete Example

Computing Training Requirements

Let's calculate the training requirements for a 1.8B parameter model (like Qwen-1.8B) using the scaling laws: 

import math

def estimate_training(precision: str = "bf16") -> dict:
    """
    Estimate compute, data, and time requirements for training an LLM.

    Uses the scaling law: C ~ 6 * N * D
    where N = parameters, D = tokens, C = FLOPs.

    Assumes optimal data = 1.7x parameters (OpenAI) or 20x (LLaMA).
    """
    # Model parameters
    params = 1.8e9  # 1.8 billion

    # Optimal data amounts
    data_openai = params * 1.7      # 3.06B tokens (OpenAI minimum)
    data_llama = params * 20        # 36B tokens (LLaMA optimal)

    # Total compute (FLOPs)
    compute_openai = 6 * params * data_openai
    compute_llama = 6 * params * data_llama

    # BF16 = 16-bit precision, so each FLOP is 16 bits
    # A100 FP16/BF16 peak: ~19.5 TFLOPS per GPU (with SPARSE disabled)
    a100_tflops = 19.5
    gpu_count = 8  # single node

    # Training time in hours (assuming 70% effective utilization)
    utilization = 0.70
    effective_tflops = a100_tflops * gpu_count * utilization

    hours_openai = compute_openai / (effective_tflops * 1e12) / 3600
    hours_llama = compute_llama / (effective_tflops * 1e12) / 3600

    return {
        "model_params_b": params / 1e9,
        "data_tokens_b_openai": data_openai / 1e9,
        "data_tokens_b_llama": data_llama / 1e9,
        "compute_flops_openai": f"{compute_openai / 1e18:.2f}E",  # ExaFLOPs
        "compute_flops_llama": f"{compute_llama / 1e18:.2f}E",
        "training_hours_8x_a100_openai": f"{hours_openai:.1f}",
        "training_hours_8x_a100_llama": f"{hours_llama:.1f}",
    }

result = estimate_training()
for key, value in result.items():
    print(f"{key}: {value}")

Output:

model_params_b: 1.8
data_tokens_b_openai: 3.06
data_tokens_b_llama: 36.0
compute_flops_openai: 0.03E
compute_flops_llama: 0.40E
training_hours_8x_a100_openai: 0.6
training_hours_8x_a100_llama: 6.9

With just 8 A100 GPUs, training a 1.8B model on the OpenAI-recommended 3B tokens takes less than an hour. But scaling to LLaMA's 20x token ratio pushes it to nearly 7 hours. Now imagine a 70B model — the same 8-GPU setup would need months, which is why models like LLaMA-70B require clusters of 1,000+ GPUs.

Comparing Model Architectures

The source material provides a useful comparison table showing how model scale has evolved:

Model Layers Hidden Size Heads Parameters Training Tokens
BERT-base 12 768 12 0.1B 3B
BERT-large 24 1,024 16 0.3B 3B
Qwen-1.8B 24 2,048 16 1.8B 2.2T
LLaMA-7B 32 4,096 32 7B 1T
GPT-3 96 12,288 96 175B 300B

Notice the gap: BERT used 3B tokens for 0.1B parameters (30x ratio), while GPT-3 used only 300B tokens for 175B parameters (less than 2x). Both worked, but the scaling laws help explain why GPT-3 was undertrained — and why LLaMA's approach of using more data per parameter produced better results at the same compute budget.

Key Takeaway: The Scaling Law C ~ 6ND means LLM training is fundamentally a resource allocation problem. For any fixed compute budget, you can trade off model size against data volume — and the optimal ratio is approximately 1.7x to 20x tokens per parameter. This formula lets you predict training time, GPU requirements, and expected model quality before writing a single line of training code.

Why It Matters

Understanding scaling laws is the difference between guessing and engineering when it comes to LLM development. Here's why this matters in practice:

  • Budget planning. Before spending $100K on GPU time, the scaling law tells you whether a 7B model on 1T tokens or a 13B model on 500B tokens gives better performance per dollar.
  • Cluster sizing. The formula tells you how many GPUs you need. A 70B model trained on 1T tokens requires roughly 420 exaFLOPs of compute. At 19.5 TFLOPs per A100 with 70% utilization, that's about 1,024 GPUs running for roughly a month.
  • Open-source benchmarking. When you see a new model claim "state-of-the-art at 7B parameters," the scaling laws help you assess whether the result is genuinely impressive or just the result of throwing more data at a standard architecture.
  • Edge deployment decisions. If you're targeting mobile or edge devices, the scaling laws help you understand the performance ceiling of smaller models. A 1B parameter model can still be very capable — if trained on enough data.

The scaling laws also explain the arms race in LLM development. Since performance improves predictably with scale, the path to better models is largely a path to more compute — which is why companies invest billions in GPU clusters and why open-source communities share training recipes so anyone with access to compute can reproduce results.

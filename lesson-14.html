Lesson 14 Chapter 7

LLM Agents — Giving Models Tools, Memory, and Autonomy

May 27, 2026 · Tool Use · Planning · ReAct Pattern · Function Calling API

The Lesson

A standard LLM is a brilliant but passive text engine: you give it a prompt, it returns text. An LLM Agent transforms that passive model into an active system that can plan, use tools, remember context, and iterate toward a goal. The analogy is sharp: a traditional LLM is like a knowledgeable librarian who can only answer questions from memory. An Agent is a personal assistant who can look things up, run calculations, make phone calls, and adjust plans based on what it learns along the way.

The architecture of an LLM Agent rests on four pillars. Goal understanding means the Agent receives a high-level objective — "plan a weekend trip to Beijing" — rather than a single prompt. Planning decomposes that goal into executable sub-steps: search attractions, check weather, compare flight prices, find hotels, call booking APIs. Memory provides both short-term context (the current conversation state) and long-term storage (retrieving information from past interactions or external knowledge bases). Tool use lets the Agent call external APIs, execute code, query databases, or search the web — bridging the gap between language understanding and real-world action.

Agents fall into several categories based on their design philosophy. Task-oriented agents focus on well-defined domains like customer service or code generation, with predefined workflows and specific toolsets. Planning and reasoning agents emphasize autonomous task decomposition, often using frameworks like ReAct (Reason + Act), where the model alternates between thinking about what to do next and executing actions. Multi-agent systems coordinate multiple specialized agents — one plans, one executes, one reviews — communicating and collaborating like a software team. Exploration and learning agents go further, actively learning from environment feedback and adjusting strategies over time, similar to reinforcement learning agents.

The technical breakthrough that made Agents practical is function calling (or tool calling) in the OpenAI-compatible API. Instead of hoping the model outputs text that you parse, the API lets you declare tools as JSON schemas. The model decides whether to call a tool, returns structured arguments, and you execute the function and feed the result back. This creates a clean loop: user → model → tool call → tool result → model → final answer. The entire cycle can repeat multiple times until the Agent reaches a satisfactory conclusion.

Concrete Example

Step 1 — Define Tool Functions

Each tool is a Python function with a clear docstring. The docstring and type hints are automatically converted into the JSON schema the API needs:

from datetime import datetime

def get_current_datetime() -> str:
    """Get the current date and time.
    Returns: A formatted string like '2026-05-27 14:30:00'."""
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

def count_letter(text: str, letter: str) -> str:
    """Count occurrences of a letter in a string.
    Args:
        text: The string to search.
        letter: The single character to count.
    Returns: The count as a string."""
    return str(text.count(letter))

def add(a: float, b: float) -> str:
    """Add two numbers together.
    Args:
        a: First number.
        b: Second number.
    Returns: The sum as a string."""
    return str(a + b)

Step 2 — Convert Functions to JSON Schema

The OpenAI API expects tools in a specific JSON format. This helper extracts function signatures using Python's inspect module:

import inspect
import json

def function_to_json(func) -> dict:
    """Convert a Python function to an OpenAI tool schema."""
    sig = inspect.signature(func)
    doc = inspect.getdoc(func) or ""

    parameters = {}
    required = []
    for name, param in sig.parameters.items():
        param_type = "string"  # default
        if param.annotation != inspect.Parameter.empty:
            if "float" in str(param.annotation) or "int" in str(param.annotation):
                param_type = "number"
            elif "bool" in str(param.annotation):
                param_type = "boolean"
        parameters[name] = {"type": param_type}
        if param.default == inspect.Parameter.empty:
            required.append(name)

    return {
        "type": "function",
        "function": {
            "name": func.__name__,
            "description": doc,
            "parameters": {
                "type": "object",
                "properties": parameters,
                "required": required,
            },
        },
    }

# Example output for get_current_datetime:
schema = function_to_json(get_current_datetime)
print(json.dumps(schema, indent=2))

Step 3 — The Agent Loop

The core Agent class manages the conversation loop: send prompt → receive response → if tool call, execute and retry → return final answer:

from openai import OpenAI
from typing import List, Dict, Any

SYSTEM_PROMPT = """You are a helpful AI assistant.
When the user's question requires using a tool, you can call the
appropriate tool from the provided tool list."""

class Agent:
    def __init__(self, client: OpenAI, model: str, tools: List = []):
        self.client = client
        self.model = model
        self.tools = tools
        self.messages = [{"role": "system", "content": SYSTEM_PROMPT}]

    def get_tool_schema(self) -> List[Dict[str, Any]]:
        return [function_to_json(tool) for tool in self.tools]

    def handle_tool_call(self, tool_call, available_tools: dict):
        """Execute a tool call and return the result message."""
        func_name = tool_call.function.name
        func_args = json.loads(tool_call.function.arguments)
        func_id = tool_call.id

        # Execute the tool
        result = available_tools[func_name](**func_args)

        return {
            "role": "tool",
            "content": str(result),
            "tool_call_id": func_id,
        }

    def get_completion(self, prompt: str) -> str:
        self.messages.append({"role": "user", "content": prompt})

        # First API call — model may request tool use
        response = self.client.chat.completions.create(
            model=self.model,
            messages=self.messages,
            tools=self.get_tool_schema(),
        )

        # If the model called a tool, execute it and call again
        if response.choices[0].message.tool_calls:
            self.messages.append({
                "role": "assistant",
                "content": response.choices[0].message.content,
            })

            tool_map = {t.__name__: t for t in self.tools}
            for tc in response.choices[0].message.tool_calls:
                print(f"Calling tool: {tc.function.name}({tc.function.arguments})")
                self.messages.append(self.handle_tool_call(tc, tool_map))

            # Second API call — model generates final answer with tool results
            response = self.client.chat.completions.create(
                model=self.model,
                messages=self.messages,
                tools=self.get_tool_schema(),
            )

        self.messages.append({
            "role": "assistant",
            "content": response.choices[0].message.content,
        })
        return response.choices[0].message.content

Step 4 — Running the Agent

Instantiate the agent and interact. Watch how the model decides when to use tools and when to answer directly:

client = OpenAI(
    api_key="YOUR_API_KEY",
    base_url="https://api.openai.com/v1",
)

agent = Agent(
    client=client,
    model="gpt-4o-mini",
    tools=[get_current_datetime, count_letter, add],
)

# Example interactions:
print(agent.get_completion("What time is it now?"))
# → Calling tool: get_current_datetime({})
# → The current time is 2026-05-27 14:30:00.

print(agent.get_completion("How many 'r's are in 'strawberry'?"))
# → Calling tool: count_letter({"text": "strawberry", "letter": "r"})
# → The word "strawberry" contains 3 occurrences of the letter 'r'.

print(agent.get_completion("What's 3.14 + 2.86?"))
# → Calling tool: add({"a": 3.14, "b": 2.86})
# → 3.14 + 2.86 = 6.0
Key Takeaway: An LLM Agent is not a different model — it's the same LLM wrapped in a control loop. The formula is Agent = LLM + Tools + Loop. The model decides what to do, the tools determine what it can do, and the loop lets it iterate until the task is done. This pattern turns a text generator into an autonomous problem solver.

Why It Matters

Agents represent the most significant shift in how LLMs are used in production. Here's why they matter:

  • Beyond hallucination-prone guessing. When a model needs to compare numbers, check the current time, or look up live data, tool calls give it ground truth. The "strawberry" problem (models famously miscounting letters) is solved by calling a counting function rather than relying on pattern matching.
  • The ReAct pattern is everywhere. frameworks like LangGraph, CrewAI, AutoGen, and OpenAI's own Assistants API all build on this core loop. Understanding the pattern lets you cut through framework complexity and see what's actually happening.
  • Multi-agent systems are the next frontier. Just as microservices replaced monoliths in backend engineering, multi-agent architectures are replacing single-LLM pipelines. Specialized agents for research, coding, review, and deployment collaborate like a team — and the coordination logic is the new engineering challenge.
  • Function calling is the standard interface. Every major provider (OpenAI, Anthropic, Google, Mistral) now supports tool/function calling natively. This is no longer a hack — it's the primary way production systems interact with LLMs.

If RAG is about giving the model access to external knowledge, Agents are about giving the model the ability to act on the world. Together, they form the two pillars of modern LLM applications: knowledge grounding and tool-assisted autonomy.

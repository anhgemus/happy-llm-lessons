ZeRO Optimization — Fitting Billion-Parameter Models on Limited GPU Memory

Memory Optimization DeepSpeed ZeRO-1/2/3

The Lesson

Training a large language model requires enormous GPU memory. For a model with millions of parameters, a single GPU can hold everything. But when models reach billions or hundreds of billions of parameters, no single GPU has enough memory — not even for the model weights alone, let alone the optimizer states and gradients needed for training.

DeepSpeed's ZeRO (Zero Redundancy Optimizer) solves this by sharding model states across GPUs instead of replicating them. In standard data parallelism, every GPU holds a complete copy of the model parameters, gradients, and optimizer states. ZeRO eliminates this redundancy by partitioning these states so each GPU only stores a fraction.

During training, ZeRO reconstructs the needed parameters on-the-fly through communication between GPUs. The trade-off is clear: more sharding means less memory per GPU, but more communication overhead. ZeRO offers three progressive levels of optimization, each trading additional communication for more memory savings.

Concrete Example

Let's work through the memory math for a 1 million parameter model trained with Adam optimizer in mixed precision (FP16 weights, FP32 optimizer states).

Memory Breakdown for 1M Parameters

Component Precision Bytes per Param Total (1M params)
Model parameters FP16 2 2 MB
Gradients FP16 2 2 MB
Adam momentum (m) FP32 4 4 MB
Adam variance (v) FP32 4 4 MB
Total model states — 12 bytes/param 12 MB

For a 7B parameter model: 12 × 7B = 84 GB in model states alone, per GPU.

With 4 GPUs (N=4), ZeRO progressively reduces per-GPU memory:

Strategy What's Sharded Per-GPU Model States (7B model)
Baseline (no ZeRO) Nothing — full replication 84 GB
ZeRO-1 Adam states only (8 MB → 2 MB/GPU) 84 GB → 56 GB
ZeRO-2 Adam states + gradients 84 GB → 42 GB
ZeRO-3 Adam states + gradients + parameters 84 GB → 21 GB

ZeRO-3 achieves a 4× reduction in model state memory on 4 GPUs. This is the difference between needing 4× A100 80GB and being able to train on 4× A100 40GB.

DeepSpeed Configuration

Here's how to enable ZeRO stages in a DeepSpeed configuration file:

{
  "optimizer": {
    "type": "Adam",
    "params": {
      "lr": 3e-5,
      "betas": [0.9, 0.999],
      "eps": 1e-8
    }
  },
  "scheduler": {
    "type": "WarmupLR",
    "params": {
      "warmup_min_lr": 0,
      "warmup_max_lr": 3e-5,
      "warmup_num_steps": 2000
    }
  },
  "zero_optimization": {
    "stage": 2,
    "allgather_partitions": true,
    "allgather_bucket_size": 2e8,
    "overlap_comm": true,
    "reduce_scatter": true,
    "reduce_bucket_size": 2e8,
    "contiguous_gradients": true
  },
  "train_batch_size": 64,
  "train_micro_batch_size_per_gpu": 4,
  "gradient_accumulation_steps": 16
}

To switch between ZeRO stages, simply change "stage": 2 to "stage": 1 or "stage": 3. For ZeRO-3, add offload options:

{
  "zero_optimization": {
    "stage": 3,
    "offload_optimizer": {
      "device": "cpu",
      "pin_memory": true
    },
    "offload_param": {
      "device": "cpu",
      "pin_memory": true
    },
    "overlap_comm": true,
    "sub_group_size": 1e9,
    "reduce_bucket_size": "auto",
    "stage3_max_live_parameters": 1e9,
    "stage3_max_reuse_distance": 1e9
  }
}

Python Training Script

import deepspeed
import torch
from transformers import AutoModelForCausalLM

# Load model and initialize DeepSpeed
model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-2-7b-hf")

# Initialize with ZeRO config
model_engine, optimizer, train_loader, _ = deepspeed.initialize(
    model=model,
    model_parameters=model.parameters(),
    training_data=train_dataset,
    config="ds_config.json"  # ZeRO config file
)

# Training loop — ZeRO handles all sharding transparently
for batch in train_loader:
    outputs = model_engine(**batch)
    loss = outputs.loss
    model_engine.backward(loss)
    model_engine.step()

Notice that the training loop looks identical to standard PyTorch. ZeRO intercepts the forward/backward/step calls and handles parameter gathering, gradient reduction, and optimizer state updates behind the scenes.

Key Takeaway

ZeRO eliminates redundant memory by sharding model states across GPUs. Each GPU stores only 1/N of the optimizer states (ZeRO-1), gradients (ZeRO-2), or even parameters (ZeRO-3). The rule of thumb: use ZeRO-1 when you're close to fitting, ZeRO-2 for moderate savings, and ZeRO-3 when you need maximum memory reduction — accepting higher communication overhead.

Why It Matters

ZeRO is the reason you can train a 7B parameter model on 4 consumer-grade GPUs instead of requiring a data center with hundreds of A100s. Every major open-source LLM — LLaMA, Qwen, Mistral — was trained using ZeRO or similar techniques.

Understanding ZeRO is essential for anyone who trains models beyond a few hundred million parameters. It directly determines your hardware budget, training time, and whether your experiment is feasible at all. The choice between ZeRO stages is one of the most impactful decisions in LLM training infrastructure.

As models continue to grow, ZeRO-3 with CPU offloading has become the standard for training on limited GPU clusters. The communication overhead is real, but the alternative — not being able to train at all — is worse.
